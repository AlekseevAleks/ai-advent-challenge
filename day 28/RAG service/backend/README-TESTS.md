# Тестирование backend

## Обычные тесты (без Ollama)

Клиент эмбеддингов подменяется на фейковый (только в тестах) — векторные индексы
строятся на детерминированных псевдовекторах размерности 8.

```bash
cd backend
.venv/bin/pytest                    # все тесты
.venv/bin/pytest tests/unit/        # только unit
.venv/bin/pytest tests/integration/ # только интеграционные
```

Что покрыто (83 теста):

**Unit**
- извлечение текста: TXT (UTF-8, CP1251, BOM, бинарные файлы), Markdown (заголовки,
  игнорирование `#` внутри блоков кода), PDF (постранично, номера страниц, предупреждение
  об OCR для сканов), DOCX (абзацы и заголовки), Python/JS (структура функций и классов),
  CSV/JSON (читаемое представление);
- fixed-size chunking: границы, overlap, пустые документы, лимит max-размера,
  токены без tiktoken → понятная ошибка, уникальность chunk_id, метаданные;
- structural chunking: заголовки Markdown и путь разделов, рекурсивное деление больших
  разделов, объединение мелких, fallback на абзацы, символы кода, страницы PDF,
  отсутствие объединения разных файлов;
- статистика (медиана, квантили, гистограмма), нормализация векторов к единичной
  длине, схема метаданных, метаданные чанков.

**Интеграционные (через HTTP API, фейковый эмбеддинг-клиент)**
- загрузка нескольких файлов (multipart), лимиты, имена-дубликаты, пустые документы;
- задание индексации обеих стратегий; сохранение/загрузка FAISS; соответствие позиций
  векторов и метаданных; нормализация; файлы на диске;
- поиск Top-K с корректными оценками; пустой индекс/запрос/модель;
- отмена задания (без частичного индекса);
- ошибка Ollama → статусы failed / completed_with_errors с видимым сообщением;
- добавление документов в существующий индекс; отказ при несовместимой конфигурации;
- перестроение индекса;
- сравнение стратегий, история, сводная статистика, статистика индекса, чанки;
- **модуль «Reranking & Filtering» (HTTP API, DI-моки, без Ollama/больших моделей):**
  - метрики Hit@K/Precision@K/Recall@K/MRR на известных наборах (включая пустые ground truth);
  - граница фильтра (`>= threshold` проходит, `<` отбрасывается; 0.65 против 0.64);
  - валидация `initial_top_k >= final_top_k` и диапазона threshold;
  - heuristic-реранкер МОЖЕТ изменить порядок retrieval; similarity-реранкер сохраняет;
  - cross-encoder без библиотеки → понятная ошибка с `install_hint` (без авто-подмены);
  - query rewriter: возвращает строку, отклоняет пустой результат/запрос, обрезает длинные;
  - полный pipeline через HTTP: baseline vs filter (порог 0/1/отрицательные косинусы),
    reranker-оценки согласованы с финальным порядком, rewrite-режим с mock-rewriter'ом;
  - evaluation: создание датасета, сравнение 6 режимов, метрики/латентность, экспорт JSON/CSV;
  - эксперименты: сохранение, чтение, сравнение двух, экспорт JSON/CSV.

## Тест с настоящим Ollama

Требуется запущенный Ollama и установленная модель `nomic-embed-text`:

```bash
ollama serve &           # или приложение Ollama
ollama pull nomic-embed-text
```

Ручной сценарий (полный путь):
1. Запустите backend: `uvicorn app.main:app --reload`
2. `curl -X POST http://127.0.0.1:8000/api/documents/demo` — демо-корпус.
3. Создайте задание через Swagger `/docs` → `POST /api/indexing/jobs`
   (`strategies: ["fixed_size","structural"]`, `mode: "new_collection"`),
   опрашивайте `GET /api/indexing/jobs/{id}`.
4. `POST /api/search` с запросом «чем полезна индексация для RAG» — проверьте,
   что Top-1 — чанк о RAG, а не случайный документ.
5. `GET /api/comparison/{collection_id}` — метрики по фактам.
